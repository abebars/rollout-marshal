### Why the alarm cleared when it did

**The load ended before the fault did.** 300 answers at most 10 in flight took about 4 minutes. So the last `cheaper` datapoint is in the 08:35 minute, and the fault ran on with no traffic until 08:37:30Z. The alarm's return to OK at 08:42:17Z therefore came from the breaching datapoints aging out of its evaluation range, not from fast answers after the fault.

CloudWatch's page on how alarms treat missing data (docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/alarms-and-missing-data.html) gives the rule:
- **The wider range.** Each evaluation retrieves "a higher number of data points than the number specified as Evaluation Periods" (the evaluation range).
- **Enough real points.** While at least 2 real points remain in the range, CloudWatch evaluates "the most recent real data points", and the missing-data setting "is not needed and is ignored". So the breaching 08:34 and 08:35 points kept the alarm in ALARM.
- **Too few real points, the third case.** "If some data points in the evaluation range are missing, and the number of actual data points that were retrieved is lower than the alarm's number of Evaluation Periods, CloudWatch fills in the missing data points with the result you specified for how to treat missing data, and then evaluates the alarm."

**When OK came.** It came when the 08:34 point left the evaluation range. The one real point left, 08:35, cannot fill 2 periods, so the missing one counted as not breaching (`notBreaching`), and 1 breaching point of 2 is not ALARM.

**The lag.** Measured from the start of the last breaching minute, the lag is 7 min 17 s: 08:35:00Z to 08:42:17.421Z. Measured the same way in 4.1's test it was 7 min 20 s: 02:37:00Z to 02:44:19.954Z (`evidence/4.1-alarm.md`). A load that outlasts the fault would show the recovery from fast answers instead. Task 4.3 fixes this run's load at 150 × 2.
