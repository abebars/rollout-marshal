## 3. How a numeric value travels on an event

The SDK turns every value into a string before it leaves: `"value": str(value) if value is
not None else None` (`analytics.py:234`). One batch is
`POST https://events.api.flagsmith.com/v1/events` (`analytics.py:147`) with body
`{"events": [...]}` (`analytics.py:392`) and headers `X-Environment-Key: <SDK key>`,
`Content-Type: application/json; charset=utf-8`, `Flagsmith-SDK-User-Agent:
flagsmith-python-sdk/6.7.0` (`analytics.py:436-440`). Each event is
`{"event", "feature_name", "identifier", "value", "traits", "metadata", "timestamp"}`,
with `metadata` gaining `sdk_version` and `timestamp` in epoch milliseconds set at track
time. An exposure is the event `$flag_exposure` with `feature_name` set
(`analytics.py:26`).

Shown with the real SDK against a local stand-in for the events API
(`app/spike/tests/test_sdk_events.py`, `uv run pytest app/spike/tests/test_sdk_events.py`):

| `value=` | Sent as |
| --- | --- |
| `1` | `"1"` |
| `0` | `"0"` |
| `0.8` | `"0.8"` |
| `1234` | `"1234"` |
| `True` | `"True"` (so `answer_helpful` must be the integer 1 or 0, as design.md says) |
| `None` | `null` |

Live: the warehouse read the strings `"1"` and `"0"` as numbers. The lead's results read
shows sums of 63 and 14 for the two arms, exactly the totals sent (section 7).

## 4. Flushing: `flush_events()` against `max_buffer_items=1`

Shown locally with the real SDK (same test file):

- Defaults, then `flush_events()`: 150 events tracked in a loop are all at the events
  endpoint, in one batch, the moment `flush_events()` returns (no sleep in the test).
- `EventProcessorConfig(max_buffer_items=1)`, the setting docs.flagsmith.com suggests for
  short scripts
  (https://docs.flagsmith.com/experimentation/set-up-with-a-coding-agent; also
  https://docs.flagsmith.com/experimentation/run-an-experiment: "In short-lived scripts
  and jobs, pass `max_buffer_items=1` to `EventProcessorConfig`"). Of 150 events tracked in
  a loop, at most 2 arrive, and the SDK logs
  `Event buffer was full: dropped the N oldest events`. Three events in a row (what rm-judge
  sends per answer) also lose events. The buffer holds one event, and each new event pushes
  out the one before it while the worker is sending (`analytics.py:385`).

So design.md's rule stands: default buffer settings plus `flush_events()` before the
handler returns. Do not set `max_buffer_items=1` in rm-router or rm-judge.

Also from the source: identical exposures (feature, identifier, value) inside one send are
sent once (`analytics.py:259`); a 401 or 403 from the events API stops event tracking for
that client (`analytics.py:448`).

Live, in the deployed function: each invocation's single batch was answered `202` before
the handler returned. The router's 150 exposures took 0.418 s to flush; the judge's 150
outcome events took 0.425 s. Lambda froze the container after each invocation; all 300
events still reached the warehouse (section 7). Flushing before the handler returns is
enough; nothing relies on buffer settings or a background thread surviving the freeze.

## 8. Findings for 1.4 and later tasks

1. **`flag.variant` per arm**: control `control`, treatment `cheaper`. `flag.value` is
   `current` or `cheaper`, and Flagsmith's results label the arms `control` and `cheaper`.
   - The router serves by `flag.value` and records `flag.variant` on the exposure.
   - Task 2.2 maps the results' `control` onto `current`.
   - The experiment's rollout appears as a segment, `experiment-807-rollout`, in
     `flag.reason`. The 50/50 split applies even though the option's environment default
     allocation is 0.
2. **Events work with the client-side key** (design.md section 8's question): every batch was
   answered `202`, and `key_is_server_side` was false. No server-side key is needed.
3. **`flush_events()` before every handler returns** is what works, in Lambda too
   (section 4).
   - `max_buffer_items=1`, which docs.flagsmith.com suggests for scripts
     (https://docs.flagsmith.com/experimentation/set-up-with-a-coding-agent), drops events
     tracked in a row. It must not be used in rm-router or rm-judge.
   - Each flush here was one synchronous POST of a 150-event batch, about 0.42 s. A
     one-exposure flush in rm-router was not measured. Its time falls outside the measured
     answer latency but inside the API Gateway request.
   - The worst case when the events API is slow or down, for task 3.2: `flush_events()`
     waits for the send to finish.
     - A send makes up to 3 attempts (`EVENTS_MAX_ATTEMPTS`), each a POST with a 3 s timeout
       (`EVENTS_REQUEST_TIMEOUT_SECONDS`).
     - Before attempts 2 and 3 it waits a random backoff of up to 1 s and then up to 2 s
       (`EVENTS_RETRY_BASE_SECONDS * 2 ** (attempt - 2)`) (`analytics.py:30-32`,
       `:394-397`).
     - That adds up to about 12 s, possibly more: requests applies a single timeout value to
       the connect and to each read separately, not to the whole request (requests' own
       behaviour, not tested here).
     - After the last transient failure the batch is kept for the next send
       (`analytics.py:428-429`), unless the last answer was a 500, which drops it
       (`:423-427`). In Lambda, a kept batch waits in a frozen container.
     - rm-router's 29 s timeout and API Gateway's 30 s should allow for those 12 s.
4. **A numeric value travels as a string** (`str(value)`). The warehouse aggregated `"1"` and
   `"0"` correctly. A Python bool would arrive as `"True"`, so send integers.
5. **Default Bedrock project permission** (for task 3.5's roles): the Converse API reference
   says a request needs `bedrock:InvokeModel` on the project as well, here
   `arn:aws:bedrock:us-east-1:818928662830:project/default`. The spike role had it.
   - Whether it is enforced was not tested; the lead decided to skip that experiment.
   - Task 3.5 should grant it to `rm-answer-current`, `rm-answer-cheaper` and `rm-judge`.
6. **boto3 in the Lambda runtime** is 1.42.97 (botocore 1.42.97), and it worked with the
   bundled urllib3 2.8.0. AWS recommends bundling boto3 in the deployment package
   (https://docs.aws.amazon.com/lambda/latest/dg/python-package.html). Whether the `app`
   group adds it is decided in 1.4 or PR-b.
7. **The SDK's own exposure checks**: `get_experiment_flag` also skips an exposure when the
   flag is disabled or `flag.variant` is None (`flagsmith.py:380`, `:392`). design.md's
   router rule checks `in_experiment` only. Here all 150 flags were enabled and had a
   variant, so the two rules gave the same result. Whether 3.2 adds the checks is decided in
   1.4 or PR-b.
8. **Request fields proven**, for 1.4's constants:
   - effort low is `{"output_config": {"effort": "low"}}`, on Fable 5.1 and on Sonnet 5;
   - thinking disabled is `{"thinking": {"type": "disabled"}}`, on Haiku 5.5 and on Sonnet 5;
   - Fable 5.1 rejects thinking disabled with the 400 quoted in section 5.
   - No sampling field was sent anywhere. The spike's guard also refuses `topK`, a spelling

     whether the runtime's botocore 1.42.97 knows it was not checked.
