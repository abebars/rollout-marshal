### 3. Section 13: can the AgentCore CLI add an MCP server target with API-key auth? **No.**

On the scratch copy only:

```
agentcore add gateway --name rm-gateway --authorizer-type AWS_IAM --protocol-type MCP --json      # exit 0
agentcore add credentials api-key --name rm-flagsmith-api-key \
  --api-key-secret-reference '{"secretId":"arn:aws:secretsmanager:us-east-1:818928662830:secret:dummy-AbCdEf","jsonKey":"key"}' --json   # exit 0
agentcore add gateway-target --gateway rm-gateway --name flagsmith --endpoint https://mcp.flagsmith.com \
  --outbound-auth api-key --credential-name rm-flagsmith-api-key --json
# Error: ✖ mcpServer targets do not support API_KEY outbound auth
#   → at agentCoreGateways[0].targets[0].outboundAuth          exit 1
```

The rule is in `@aws/agentcore-cdk` 1.3.0, `schema/schemas/mcp.js`, `TARGET_TYPE_AUTH_CONFIG`:
`mcpServer: { validAuthTypes: ['OAUTH', 'NONE', 'GATEWAY_IAM_ROLE'] }`, so no path through
`agentcore.json` gets there. The AgentCore API itself supports it: the outbound-auth table
lists "MCP server ... API key: Yes"
(docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-outbound-auth.html), and
CreateGatewayTarget takes `credentialProviderType: API_KEY` with `credentialParameterName`,
`credentialPrefix` and `credentialLocation`. Hence `agent/scripts/setup_gateway.py` uses
boto3. The CLI's credential path was also ruled out: it either keeps the key in
`agentcore/.env.local` or needs a Secrets Manager reference with a `jsonKey`, while
`rm/flagsmith/api-key` holds a bare string.

put back at 22:32:31Z (same command with `"credentialPrefix":"Api-Key "`; READY, stored as

No call failed: both prefixes authenticated, because the service drops the trailing space
(observed) and, by the inference above, the Gateway adds the separator. The value the
service stores is `Api-Key` without the space; 1.4 sets `GATEWAY_API_KEY_PREFIX` to that.
`admin_api.py` and the direct transport in `agent.py` build the header as the prefix
stripped plus one space, so they send `Api-Key <key>` with either value (unit tests call
the real builders with both). The same read through the deployed agent at 22:35:38Z (`{"action": "read", "tool":

**Finding: the running experiment's feature is not locked against API writes.** Flagsmith

**How a feature's state changes with v2 feature versioning** (Development and Production
both have `use_v2_feature_versioning: true`; for 2.2's `set_kill_switch` and
`set_default_model`). `update_environment_feature_state` does not apply there (its tool
description: "Applies to environments without v2 feature versioning"). Four MCP calls,
each shown above:

1. `create_environment_feature_version {environment_pk, feature_pk}` creates an unpublished
   version with a copy of the live states and returns its `uuid`.
2. `get_environment_feature_version_states {environment_pk, feature_pk,
   environment_feature_version_pk: <uuid>}` lists them; the environment default has
   `feature_segment null`.
3. `update_environment_feature_version_state {environment_pk, feature_pk,
   environment_feature_version_pk: <uuid>, id__path: <state id>, feature: <feature id>,
   enabled: <bool>, feature_state_value: <the state's value object, e.g. {"type":
   "unicode", "string_value": "current"}>}` changes it (`feature_state_value` is required;
   for a string flag like `assistant_default_model` it carries the new string).
4. `publish_environment_feature_version {environment_pk, feature_pk, id: <uuid>}` makes it
   live (`live_from` in the reply).

`create_environment_feature_version` also takes `feature_states_to_update` and
`publish_immediately` (one call); that form was not exercised.
